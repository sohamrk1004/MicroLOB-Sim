# Performance Analysis

## Purpose

This document evaluates the computational performance of the Phase 1 limit order book implementation. It examines the expected complexity of the implemented data structures and operations, the trade-offs between different data structure choices, and the cancellation benchmark results collected during Phase 1.

The goal is to understand how the engine's operations scale as the number of orders increases. The analysis distinguishes theoretical complexity from measured execution time because a data structure that is simple to implement may not remain efficient when its workload grows.

The matching engine prioritizes correctness, deterministic behavior, and a clear implementation of continuous double auction mechanics. Performance improvements must preserve these properties. The benchmark results provide a baseline for identifying operations that may become bottlenecks as the project develops.

## Complexity Variables

Several quantities are relevant when analyzing the engine.

| Variable | Meaning |
|---|---|
| `P` | Number of active price levels |
| `N` | Number of orders in the relevant book or queue |
| `K` | Number of orders processed during a matching operation |
| `L` | Number of price levels visited during matching |
| `T` | Number of trades generated by an operation |
| `M` | Number of recorded market events |

These variables are not interchangeable. An order book containing many orders may have relatively few active price levels, while another book with the same number of orders may have a much larger number of price levels. The cost of an operation depends on the specific structure it interacts with.

## Baseline Architecture

The Phase 1 engine uses dictionaries to organize price levels and FIFO order queues to preserve time priority within each level. This design separates the price-level structure from the orders resting at a particular price.

The dictionary provides direct access to a price level when its price is already known. Operations that need to determine the best available price may still need to inspect the existing price keys. Order queues preserve the sequence in which orders arrive at the same price, which is necessary for price-time priority.

The current architecture is intentionally straightforward. It allows the matching engine to implement market rules explicitly without introducing unnecessary data structure complexity. Its performance limitations are mainly associated with searching through orders and determining price-level priority.

## Dictionary-Based Price Levels

Price levels are stored using a dictionary keyed by price.

Dictionary operations such as retrieving an existing price level, inserting a new key, or removing a key have average-case complexity of `O(1)` under normal hashing assumptions.

| Operation | Expected complexity |
|---|---|
| Retrieve a known price level | `O(1)` average |
| Insert a price level | `O(1)` average |
| Remove a known price level | `O(1)` average |
| Check whether a price level exists | `O(1)` average |
| Iterate through all price levels | `O(P)` |

The dictionary does not automatically maintain price priority. It provides access to levels by price, but finding the highest bid or lowest ask may require examining the available price keys.

This distinction matters because direct price lookup and best-price discovery are different operations. The first is efficient when the price is known. The second depends on the number of active price levels.

## Best Bid and Best Ask Retrieval

The best bid is the highest active buy price, while the best ask is the lowest active sell price.

If the implementation scans the dictionary keys to identify the best available price, retrieval requires examining the active price levels.

| Operation | Complexity |
|---|---|
| Best bid retrieval through scanning | `O(P)` |
| Best ask retrieval through scanning | `O(P)` |

The cost depends on the number of price levels rather than the total number of orders. If many orders share the same price, the number of price levels can remain relatively small even as the order book grows.

A structure that maintains price levels in sorted order could reduce the cost of retrieving the best price. However, it would also introduce additional complexity when inserting and removing levels. The baseline implementation does not use a more advanced sorted-price structure because the initial goal is a transparent and correct matching engine.

## FIFO Order Queues

Orders at the same price level must be processed according to time priority. The earliest resting order at a price receives priority over later orders at that same price.

A list-based queue supports appending new orders efficiently. Accessing the first order is also straightforward. Removing an order from the front or from an arbitrary position requires shifting the remaining elements in the list.

| Queue operation | Complexity |
|---|---|
| Append an order to the end | `O(1)` amortized |
| Access the first order | `O(1)` |
| Search for an order by ID | `O(N)` |
| Remove the first order | `O(N)` |
| Remove an order at an arbitrary position | `O(N)` |

The main limitation is not insertion at the end of the queue. It is the cost of locating and removing an order that is not necessarily at the front.

This affects cancellation because an order can be cancelled regardless of its position in the resting queue. A list-based queue must locate the order and then remove it. Both operations can require traversal through the queue.

## Order Insertion

Order insertion depends on whether the order can be added to an existing price level or whether a new price level must be created.

When the price level already exists, the dictionary can locate it in average `O(1)` time. Appending the order to the FIFO queue is amortized `O(1)`.

When the price level does not exist, a new level must be created and inserted into the dictionary. The dictionary insertion itself is average `O(1)`. Additional work may be required later to determine the best price because the dictionary does not maintain price ordering.

The insertion operation therefore has a relatively low direct cost when a known price level exists. The overall cost of processing an incoming order can be greater because it may also require matching, price-level discovery, trade recording, and order-book updates.

## Order Matching

Matching is the operation that determines whether an incoming order can execute against resting orders on the opposite side of the book.

The process may involve:

- Determining the best available price on the opposing side.
- Checking whether the incoming order is compatible with that price.
- Accessing the resting order at the front of the price-level queue.
- Executing the trade.
- Updating remaining quantities.
- Removing fully executed orders.
- Removing price levels that become empty.
- Continuing until the incoming order is filled or no further matching is possible.

The cost of matching depends on the number of resting orders processed and the number of price levels visited. A simplified traversal model is `O(K + L)`, excluding the additional costs associated with best-price discovery, data structure operations, trade recording, and other bookkeeping.

This is not a complete worst-case bound for every matching operation. The actual implementation cost depends on how frequently price levels are searched and how many queue elements are removed during execution.

A matching operation that executes against only one resting order may perform considerably less work than an operation that walks through many orders across multiple price levels.

## Order Cancellation

Cancellation is one of the operations directly examined through the Phase 1 benchmark.

In the baseline list-based structure, cancellation requires locating an order in the resting queue. Once located, the order must be removed. Searching a list requires examining its elements until the target is found, while removing an element from a list may require shifting subsequent elements.

The expected complexity of cancellation is therefore linear in the number of resting orders in the relevant search structure.

| Cancellation step | Complexity |
|---|---|
| Search for the target order | `O(N)` |
| Remove the order from a list | `O(N)` |
| Remove an empty price level from the dictionary | `O(1)` average |
| Overall list-based cancellation | `O(N)` |

The overall operation remains linear because the order search and list removal are linear. Removing an empty price level from the dictionary does not change this scaling behavior.

The benchmark was designed to examine how cancellation time changes as the number of resting orders increases. The results are presented in the benchmark section below.

## Empty Price-Level Removal

A price level should not remain in the order book after its queue becomes empty.

Removing an empty level from the dictionary is an average `O(1)` operation when the price is already known. The difficulty is not the dictionary removal itself. It is maintaining the correct book state and ensuring that the removal happens only when the queue contains no resting orders.

This operation is important for both correctness and performance. Empty levels would otherwise accumulate and increase the number of price keys that the engine must inspect when searching for the best price.

## Order Lookup

Order lookup is an important part of cancellation and other operations that require access to a particular order.

The baseline implementation uses the order queues as the primary structure for resting orders. Locating an order by its ID requires searching through the relevant queue or queues, depending on the lookup implementation.

| Lookup approach | Expected complexity |
|---|---|
| Search a list of orders | `O(N)` |
| Search a linked queue without a node reference | `O(N)` |
| Dictionary mapping order ID to order or node | `O(1)` average lookup |

A separate order-ID index could improve lookup performance. It would introduce another structure that must remain consistent with the order book whenever an order is inserted, executed, cancelled, or removed.

This creates an architectural trade-off. A faster lookup structure may reduce the cost of cancellation, but maintaining multiple representations of the same order state introduces additional failure conditions and consistency requirements.

## Data Structure Alternatives

Several data structures were considered in relation to the engine's operations.

| Data structure | Relevant advantages | Relevant limitations |
|---|---|---|
| List | Simple, readable, efficient append, easy FIFO representation | Linear search and removal costs |
| Deque | Efficient operations at both ends | Arbitrary order removal and lookup are not constant time |
| Singly linked queue | Efficient removal when the node is already known | Searching for the node remains linear |
| Doubly linked queue | Efficient removal when the node is known, including middle positions | More memory and pointer management |
| Dictionary | Average constant-time access by known key | Does not maintain sorted price order |
| Dictionary with order-ID index | Average constant-time order lookup | Additional state must remain consistent |
| Sorted price structure | Efficient best-price access | More complicated insertion, deletion, and maintenance |

A linked queue can make the removal of a known node efficient. However, it does not automatically make cancellation efficient. If the engine still needs to search through the queue to find the order, lookup remains `O(N)`.

A linked queue combined with an order-ID dictionary could allow the engine to locate a node in average `O(1)` time and remove it in `O(1)` time. This would improve the cancellation operation, but it would require careful maintenance of the index during every order lifecycle transition.

The benchmark provides a baseline for evaluating whether this added complexity would be justified by the observed performance of the existing implementation.

## Cancellation Benchmark

### Experimental Setup

The cancellation benchmark measures the time required to cancel orders from list-based resting queues at different queue sizes.

Six queue sizes were tested:

- 100 resting orders
- 1,000 resting orders
- 5,000 resting orders
- 10,000 resting orders
- 25,000 resting orders
- 50,000 resting orders

Each queue size has 30 recorded measurements, producing a total of 180 measurements.

The benchmark data is stored in `cancellation_baseline.csv`. The individual measurements are recorded in nanoseconds. The comparison uses median cancellation time as the primary statistic because individual timing measurements can be affected by runtime variation and occasional unusually slow observations.

The mean is also reported to show how the measurements are affected by higher timing values. The minimum and maximum provide the observed range for each group.

### Results

The following results were calculated from the recorded benchmark data.

| Resting orders | Median (ns) | Median (μs) | Mean (μs) | Minimum (μs) | Maximum (μs) |
|---:|---:|---:|---:|---:|---:|
| 100 | 2,700 | 2.70 | 3.02 | 2.60 | 7.80 |
| 1,000 | 25,750 | 25.75 | 40.34 | 20.00 | 160.60 |
| 5,000 | 138,700 | 138.70 | 160.55 | 105.30 | 349.20 |
| 10,000 | 248,600 | 248.60 | 291.56 | 218.80 | 549.00 |
| 25,000 | 517,100 | 517.10 | 521.85 | 486.90 | 571.30 |
| 50,000 | 1,127,150 | 1,127.15 | 1,253.77 | 1,078.90 | 2,646.00 |

The median cancellation time increases consistently across all six queue sizes. At 100 resting orders, the median is 2.70 microseconds. At 50,000 resting orders, it reaches 1,127.15 microseconds, or approximately 1.127 milliseconds.

The measurements show that cancellation becomes more expensive as the queue grows. The largest queue takes substantially longer to process than the smallest queue.

### Median Scaling

The median timing at 50,000 resting orders is approximately 417.5 times the median timing at 100 resting orders.

The queue size increased by a factor of 500 over the same comparison. These scaling factors are reasonably close, although they are not identical.

| Queue size | Median cancellation time | Relative to 100 orders |
|---:|---:|---:|
| 100 | 2.70 μs | 1.00× |
| 1,000 | 25.75 μs | 9.54× |
| 5,000 | 138.70 μs | 51.37× |
| 10,000 | 248.60 μs | 92.07× |
| 25,000 | 517.10 μs | 191.52× |
| 50,000 | 1,127.15 μs | 417.46× |

The increase is broadly consistent with the expected linear scaling of list-based cancellation. The data does not establish an exact mathematical complexity class by itself. It supports the conclusion that the measured cancellation operation behaves consistently with linear growth over the tested range.

### Benchmark Variability

The individual measurements are not identical within each queue size. This is expected in runtime benchmarking because execution time can vary due to the environment and other runtime effects.

The 1,000-order group contains a particularly wide observed range. Its minimum was 20.00 microseconds and its maximum was 160.60 microseconds. Its mean is therefore considerably higher than its median.

The 50,000-order group also contains a large upper-range observation. Its maximum was 2,646.00 microseconds, compared with a median of 1,127.15 microseconds.

The median is a better primary statistic for comparing the queue sizes because it is less affected by these unusually high observations. The mean remains useful for showing that some cancellations take considerably longer than the typical measurement.

The benchmark does not treat these differences as evidence of a different complexity class. They are recorded as variability within the experiment.

### Interpretation

The cancellation benchmark supports the theoretical analysis of the list-based queue.

Searching for an order and removing it from a list requires work that grows with the number of resting orders. The measured median cancellation times increase as the queue sizes increase, and the overall scaling is broadly consistent with this linear behavior.

The experiment also demonstrates why a theoretically simple implementation can become less efficient as the order book grows. The list structure is easy to understand and supports the required FIFO behavior, but cancellation requires traversal and removal operations that become more expensive at larger queue sizes.

The benchmark is a baseline for the current implementation. It is not a comparison between multiple cancellation architectures, and it does not establish that a linked queue or indexed structure would necessarily perform better in the complete engine.

## Benchmark Limitations

The cancellation experiment covers six queue sizes with 30 repetitions per size. It provides useful evidence about scaling within the tested range, but it does not cover every possible queue size or workload.

The experiment measures cancellation time under the benchmark's setup. It does not represent the complete runtime cost of processing a market event through the engine. Matching, best-price discovery, trade recording, event logging, invariant auditing, and other operations may contribute additional runtime in normal execution.

The benchmark also does not provide a direct comparison against an alternative queue implementation. The theoretical advantages of a linked queue or order-ID index are discussed separately and have not been established through this cancellation experiment.

No hardware-specific or environment-independent performance claim is made from these results.

## Profiling Considerations

The cancellation benchmark measures one operation under a controlled queue-size experiment. A broader performance profile is necessary to understand the runtime distribution of the complete engine.

Potential areas for profiling include:

- Best bid and best ask retrieval.
- Price-level lookup.
- Order insertion.
- Cancellation search and removal.
- Matching across multiple orders.
- Matching across multiple price levels.
- Trade recording.
- Event recording and replay.
- Snapshot generation.
- Invariant auditing.

Profiling should distinguish the cost of the engine's core operations from the cost of validation and instrumentation. Invariant auditing is useful for checking internal state, but it may introduce additional work that should not be confused with the core matching algorithm's execution cost.

The cancellation baseline should remain available for comparison after any architectural change. A future implementation can be tested using the same queue sizes and repeated measurements to evaluate whether the change improves cancellation performance.

## Architectural Trade-Off

The baseline architecture prioritizes implementation clarity and correctness.

Lists provide a direct representation of FIFO queues. Dictionaries provide access to price levels by price. The resulting code is relatively easy to inspect and reason about, which is important for a matching engine where order priority and quantity accounting must remain correct.

The main performance limitation identified in this analysis is the cost of locating and removing an arbitrary order from a list-based queue. The cancellation benchmark confirms that the cost increases substantially as queue size grows.

A more advanced structure could improve cancellation performance. A linked queue with an order-ID index, for example, could reduce the cost of finding and removing an order. However, the engine would then need to maintain the index correctly during insertion, partial execution, full execution, cancellation, and empty-level removal.

The current design is therefore retained as a baseline rather than replaced solely because another data structure has a better theoretical operation cost. Any future change should be supported by a measured performance improvement and a correctness audit of the additional state it introduces.

## Conclusion

The Phase 1 implementation uses straightforward data structures that make the matching engine easier to understand and validate. Their operation costs vary depending on whether an operation accesses a known key, searches through a queue, or traverses multiple price levels.

The cancellation benchmark provides quantitative evidence that the current list-based cancellation operation becomes slower as the number of resting orders increases. Median cancellation time rises from 2.70 microseconds at 100 orders to 1,127.15 microseconds at 50,000 orders. The observed scaling is broadly consistent with the expected linear behavior of searching and removing an order from a list.

This establishes a performance baseline for the engine. The results support the theoretical complexity discussion while keeping the conclusion limited to the tested implementation and workload. Future architectural changes can use the same benchmark to determine whether improved cancellation performance justifies the additional complexity of maintaining a more advanced order structure.

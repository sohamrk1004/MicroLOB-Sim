# Performance Analysis

## Purpose

This document evaluates the computational performance of MicroLOB-Sim's matching engine. It examines the cost of its main operations, the data structures used to maintain the order book, alternative structures considered during development, and the reasoning behind the final architecture.

The technical documentation describes how the engine works. This document focuses on how that design affects runtime, memory use, and scalability. The analysis separates theoretical complexity from measured behavior because an operation with a favorable asymptotic cost does not necessarily perform better in a small Python workload.

## Baseline Architecture

The matching engine organizes orders by side and price level. Each side maintains price levels in a dictionary, while orders at a given price are stored in a FIFO queue. This separates price priority from time priority.

The dictionary provides direct access to a price level when its price key is known. The order queue preserves the arrival order of orders at that level. Matching therefore works by identifying the best opposing price, accessing its queue, and processing orders in their priority order.

The architecture was intentionally kept straightforward during Phase 1. The primary requirement was correct and predictable matching behavior. Data-structure changes were considered only when their performance benefits could justify the additional implementation and maintenance cost.

## Complexity Variables

The analysis uses the following variables.

| Variable | Meaning |
|---|---|
| `P` | Number of active price levels on a side of the book |
| `N` | Number of orders stored in a queue or book, depending on the operation |
| `K` | Number of orders actually processed during a matching operation |
| `L` | Number of price levels visited during a matching operation |
| `T` | Number of trades generated by an execution |
| `M` | Number of events in a replay or processing sequence |

These quantities are not interchangeable. A matching operation may process only a few orders even when the book contains many orders. Cancellation may require searching a large queue even though matching would not visit those orders.

## Dictionary-Based Price Levels

The order book uses dictionaries to organize price levels. A dictionary is useful because the engine frequently needs to access, insert, or remove a level using a known price.

Average dictionary lookup, insertion, and deletion are O(1). This does not mean every operation involving prices is constant time. Retrieving the best bid or best ask can require examining the available price keys when the implementation does not maintain a separate structure for the best price.

The distinction is important. A dictionary efficiently retrieves a level when its key is already known. It does not automatically provide the highest bid or lowest ask.

### Price-Level Operations

| Operation | Expected complexity |
|---|---:|
| Access level by known price | O(1) average |
| Insert a new price-level key | O(1) average |
| Remove a known price-level key | O(1) average |
| Check whether a known price exists | O(1) average |
| Find the best price by scanning keys | O(P) |
| Inspect all price levels | O(P) |

These are average-case expectations for Python dictionary operations. They do not represent worst-case guarantees for every possible dictionary configuration.

## Best Bid and Best Ask Retrieval

The best bid is the highest price among active buy levels. The best ask is the lowest price among active sell levels.

If the engine scans the dictionary keys to identify the best price, the retrieval cost grows linearly with the number of active price levels.

For a side containing `P` active levels:

- Best bid retrieval requires examining the available bid prices.
- Best ask retrieval requires examining the available ask prices.
- The cost is O(P) when the price levels are scanned.

The number of orders at each price does not directly affect this operation because only the price-level keys are needed.

This is a limitation of the current architecture. The dictionary provides efficient access to known prices, but the best-price operation still requires a search. A future implementation could maintain the best price separately or use a data structure designed for ordered prices. Such a change would introduce additional state that must remain consistent when orders enter, execute, or cause a level to disappear.

For Phase 1, the current approach was accepted because it is easy to inspect and reason about. Optimizing best-price retrieval would need to be justified by measurements showing that price-level scanning is a meaningful bottleneck.

## FIFO Order Queues

Orders at the same price must preserve time priority. The queue therefore needs to maintain the order in which orders arrived.

The current list-based approach has several useful properties. Appending a new order is simple, accessing the first order is straightforward, and iterating through orders follows their priority order. The implementation is also easy to inspect and test.

However, a Python list is not equally efficient for every queue operation.

| Operation | List complexity |
|---|---:|
| Append at the end | O(1) amortized |
| Access first element | O(1) |
| Access by index | O(1) |
| Iterate through queue | O(N) |
| Search for an order | O(N) |
| Remove first element using `pop(0)` | O(N) |
| Remove an arbitrary element | O(N) |

Removing the first element requires shifting the remaining elements. Searching for a specific order also requires examining the queue until the order is found. These operations become more expensive as the queue grows.

The list was retained because the queue operations remain simple and the Phase 1 engine prioritizes correctness, clarity, and testability. This does not mean the list is the most efficient possible structure for a large order queue.

## Order Insertion

Order insertion can involve more than one operation. The engine must determine whether the incoming order crosses the opposing side, process any available liquidity, and place any remaining quantity into the appropriate price level.

When a new price level is required, dictionary insertion is expected to take O(1) average time. When a price level already exists, appending the order to its FIFO queue is O(1) amortized.

The total cost depends on whether matching is required before the order can rest.

For a non-crossing order that enters an existing price level, the insertion process is relatively inexpensive. Creating a new level also involves dictionary insertion. The overall operation may still include validation, accounting, order registration, or other state updates that are not captured by the queue insertion complexity alone.

## Matching

Matching is not a single constant-time operation. An incoming order may execute against several resting orders at one price, continue into another price level, partially execute, or finish completely.

The matching process is bounded by the amount of opposing liquidity it actually processes. The relevant variables are the number of orders visited and the number of price levels traversed.

For a matching operation that processes `K` resting orders across `L` price levels, the basic traversal cost is related to O(K + L). This is a simplified model of the matching traversal. It excludes the additional cost of queue removal, price-level deletion, trade-record creation, accounting, and other implementation-specific operations.

The cost of matching therefore depends on the execution path. A small incoming order that executes against one resting order may require little work. A large incoming order that consumes many orders across several price levels requires more processing.

Partial fills also affect the amount of work. When an incoming order is only partially executed against a resting order, both order states must be updated. When an order is fully consumed, it must be removed from the active queue. If a price level becomes empty, the level itself must be removed from the book.

Matching complexity is therefore better described by the work performed than by the total number of orders in the book alone.

## Cancellation

Cancellation was an important part of the Phase 1 performance investigation because the current queue structure requires searching for an order before removing it.

When cancellation identifies the order through a search of its queue, the search cost is O(N) in the queue length. Removing the located order from a Python list is also O(N) in the worst case because the remaining elements may need to shift.

The exact cost depends on the order's position and the number of orders at that price. Cancelling an order near the beginning of a queue may require fewer comparisons than cancelling an order near the end, but the list removal still has linear movement cost.

| Cancellation component | Complexity |
|---|---:|
| Search for target order in queue | O(N) |
| Remove target from list | O(N) |
| Remove empty price level after cancellation | O(1) average, once identified |
| Overall cancellation at a price level | O(N) |

The linear cancellation cost is an accepted limitation of the baseline architecture. The decision to retain the simpler structure was not based on cancellation being constant time. It was based on avoiding additional data-structure complexity without sufficient evidence that the alternative would be necessary for the Phase 1 requirements.

## Empty Price-Level Removal

A price level must be removed when its queue becomes empty. Leaving empty levels in the active book would make the representation inconsistent with the intended book state and could interfere with best-price retrieval and matching.

Once the empty level has been identified, dictionary deletion is expected to take O(1) average time.

The deletion itself is inexpensive. The larger cost may come from the preceding operation that determines whether the level is empty and from the queue operation that removed the final order.

## Order Lookup and Cancellation Architecture

The baseline cancellation approach requires finding the active order within its queue. This makes cancellation dependent on queue length.

An alternative architecture would maintain a mapping from order IDs to the corresponding order and queue position. With a suitable structure, the engine could locate an order directly instead of searching every order in its price level.

A linked queue could support removal of a known node in O(1). Combined with an order-ID mapping, this could reduce cancellation to average O(1) lookup plus O(1) node removal, assuming the mapping is maintained correctly.

The additional mapping introduces its own requirements. Every insertion, execution, cancellation, and completion must update the registry correctly. A stale mapping could point to an order that is no longer active. An order removed from a queue but retained in the mapping could produce incorrect cancellation behavior. These failure modes would require additional invariant checks and tests.

The alternative is therefore not simply faster cancellation. It is a different architecture with more state and more consistency requirements.

## Data-Structure Alternatives

Several structures were considered during the Phase 1 investigation.

| Structure | Main advantage | Main limitation |
|---|---|---|
| List | Simple, readable, indexed access | Linear search and removal |
| Deque | Efficient removal from either end | Arbitrary order removal is not efficient |
| Linked queue | Efficient removal of known nodes | Searching still requires traversal without a registry |
| Doubly linked queue | Efficient removal when node is known | More pointer state and integrity requirements |
| Dictionary | Efficient lookup by known key | Does not maintain sorted keys or best-price order |
| Dictionary plus order-ID mapping | Direct order lookup | Requires registry consistency |
| Ordered price structure | Efficient ordered-price operations depending on implementation | More complex maintenance and implementation |

A deque would improve front-removal compared with a list, but it would not directly solve arbitrary cancellation by order ID. A linked queue would also require traversal to locate an order unless another mapping were maintained.

A linked queue combined with an order-ID registry offers the most direct path toward efficient arbitrary cancellation. It also introduces a larger correctness surface. The engine would need to maintain the queue links, order references, registry entries, and price-level state through every state transition.

The alternatives were evaluated in terms of their operational benefits and implementation costs rather than only their theoretical complexity.

## Benchmarking and Observed Performance

The Phase 1 benchmark work was intended to investigate cancellation scaling across increasing queue sizes. The planned sizes included 100, 1,000, 5,000, 10,000, 25,000, and 50,000 orders, with multiple runs to reduce the effect of individual timing fluctuations.

The matching performance profile examined the matching loop, price-level access, order lookup, cancellation, and snapshot generation. Profiling also introduced its own overhead, so profiler output was treated as diagnostic evidence rather than an exact representation of normal runtime.

The theoretical analysis provides expectations about how operations should scale. Benchmark results are required to determine how the implementation behaves under the tested workload.

Measured runtime can be affected by:

- The size and shape of the order book
- The position of the cancelled order
- The number of price levels
- The number of orders processed during matching
- Trade-record creation
- Invariant auditing
- Python interpreter overhead
- Operating-system scheduling
- Benchmark setup and measurement overhead

A benchmark should therefore describe the operation being measured and the workload used to produce it. A cancellation benchmark with all orders at one price measures queue search and removal behavior. A matching benchmark with many price levels measures a different combination of operations.

No numerical performance claim is made here without the corresponding verified benchmark output. The benchmark results should be recorded from the actual experiment rather than reconstructed from expected complexity.

## Profiling

Profiling was used to investigate which parts of the engine contribute to runtime. The purpose was to identify areas worth examining, not to assume that the operation with the worst theoretical complexity is necessarily the dominant bottleneck.

A profiler can show the time associated with individual functions and the frequency with which they are called. This helps identify whether runtime is dominated by matching, queue operations, book inspection, invariant auditing, or another part of the execution path.

The profiler's reported time must be interpreted carefully. Instrumentation changes the execution environment, and a function with high cumulative time may be expensive because it is called frequently rather than because each call is slow.

Invariant auditing is particularly relevant to performance measurements. It performs additional checks over the state of the book and may contribute substantial runtime during audit-heavy workloads. That cost should be separated from normal matching-engine operation when evaluating engine performance.

Profiling is useful for locating potential bottlenecks. Benchmarking is needed to measure the effect of a change under controlled conditions.

## Benchmark Interpretation

The complexity of an operation and its observed runtime answer different questions.

Theoretical complexity describes how the amount of work is expected to grow as input size increases. A benchmark measures elapsed time for a particular implementation, environment, and workload.

A linear operation can remain fast at small input sizes. A theoretically constant-time operation can still have significant overhead. Python object creation, function calls, memory allocation, and bookkeeping can affect measured results even when the asymptotic operation is efficient.

Benchmark results should not be used to claim that one data structure is universally faster. They should be interpreted in relation to the specific operation, workload, input size, and implementation.

The cancellation benchmark is particularly useful for investigating list-based removal because its cost is expected to grow with queue length. The matching benchmark is useful for examining how execution workload affects runtime, but its results must be interpreted using the number of orders and price levels actually processed.

## Architectural Trade-Off

The baseline architecture favors clarity and a smaller number of interacting state structures.

The dictionary-based price levels provide direct access to known prices. The list-based FIFO queue preserves time priority in a familiar structure. The matching and cancellation logic remain relatively easy to inspect, debug, and test.

The main limitation is that the list requires linear search and removal for arbitrary cancellation. Best-price retrieval also requires scanning available price keys when no separate best-price structure is maintained.

An alternative linked queue with an order-ID mapping could improve cancellation efficiency. That improvement would come with additional memory use and the responsibility of maintaining multiple representations of active order state. The architecture would require more tests for stale references, pointer integrity, registry consistency, order completion, and cancellation after partial execution.

For Phase 1, the simpler structure was retained because the engine's primary objective was a correct and explainable computational mechanism. A more complex structure should be introduced when measurements and future requirements demonstrate a clear benefit.

## Limitations

This analysis does not establish production-exchange performance. The benchmarks are specific to the current Python implementation and tested workloads.

The theoretical complexity estimates do not include every operation performed by Python internally. They also do not represent the worst-case behavior of every runtime operation.

The engine has not been established as an exact replica of a real exchange's infrastructure, throughput, latency, or operational behavior. The current architecture is a research and learning foundation, and its performance conclusions should remain within that scope.

Performance measurements can also change as the implementation evolves. A change to queue representation, order lookup, best-price retrieval, invariant auditing, or trade recording may alter the observed profile. Benchmark results should therefore be associated with the implementation version that produced them.

## Conclusion

The Phase 1 architecture provides a straightforward way to maintain price levels, preserve FIFO order, execute matching, and manage order state. Its dictionary-based price levels make known-price access efficient, while the list-based queues keep order sequencing and state changes easy to inspect.

The main performance limitations identified by the architecture are linear best-price scanning, queue search during cancellation, and list removal costs. Alternative structures could address some of these limitations, but they would also introduce more state and additional correctness requirements.

The current design was retained because the Phase 1 objective was to establish a correct, testable, deterministic matching mechanism before introducing optimization complexity. Future architectural changes should be based on verified benchmark evidence, specific bottlenecks, and requirements that the existing structure cannot satisfy efficiently.

Optimization should follow measurement. Complexity should be introduced only when its benefits are clear enough to justify the additional implementation and maintenance cost.
